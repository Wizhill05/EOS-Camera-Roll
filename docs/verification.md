# Verification for 0.6.4

The physical-camera failure persisted on 0.6.3. This build removes playback entirely; the build environment has not verified recovery on the user's physical camera or handset. See [the investigation](network-lockup.md) for confirmed source defects, hypotheses and the limits of the earlier streaming tests.

The current checks exercise:

- Thirty Android API 34 Robolectric workflows covering the square dark/light gallery, full-resolution JPEG viewer, portrait thumbnails and offline cache reuse, ratings and saved marks, photo Lightroom staging, restored/empty/unreachable libraries, and document-provider transfers and notifications. New checks verify a video viewer with no player and no HTTP requests; rating and background/resume without streaming; explicit video Save with one normal GET and no playback intent; a camera fixture that locks after Range remaining usable; thumbnail-only video browsing; one failed thumbnail stopping queued requests until refresh; and allowing a small thumbnail to finish before another client starts.
- Twenty host protocol checks, seven link-parser checks and forty-four media/network checks. These cover unchanged original video bytes and SHA-256, no request for a pre-cancelled save, cross-client serialization, queued cancellation without opening a socket, ownership retained during stalled cleanup, a subsequent successful request after cleanup, oversized bodies rejected before reading, trickling bodies stopped by a deadline, and folder scans stopping on transport loss.
- Actual release DEX inspection rejects player, video data-source, remote-video and metadata-retriever references and executable HTTP Range header constants. This check accepts the new APK and rejects the published 0.6.3 APK. It runs in the release script.
- Release build and lint, package/version metadata, original update signing identity, checksum and 16 KiB ZIP alignment. Native video download-only and gallery renders are reviewed.

The fake camera's lock-after-Range behavior models one possible failure. It is not a reproduction of Canon firmware or evidence that the exact cause is known. No physical-camera throughput or firmware recovery claim follows from these tests.

Screenshots are software renders of native Android views under Robolectric. They do not prove handset GPU, system file-provider, video-codec or Adobe app behavior. The photo fixture derives from the public-domain EOS R50 V RAW at https://raw.pixls.us/getfile.php/8403/nice/Canon%20-%20EOS%20R50%20V%20-%20RAW%20%283%3A2%29.CR3. Published source hash: `955ff98710505498ce7f98cbcc5875793ef2d6941b3b5692ed3baf2817ee7c9f`. It was rendered at 6048 × 4020 using the pinned LibRaw source, then cropped into test-only thumbnail variations. If that sample is unavailable during a clean test build, the layout test uses generated bitmap fixtures instead. Test photos are not bundled as user media in the app.

Still requires physical-device checking: this gallery's touch/scroll behavior; orientation on the user's own camera files; camera reconnection through the live hotspot; background service behavior under the phone vendor; ARM64 RAW memory/performance; physical video original transfers and camera recovery; actual Lightroom import/cleanup. A fixture-based portrait test is not evidence that the user's exact files have been examined.

The traffic assertions measure requested paths, response usage and request counts against a local camera fixture. They are not a claimed handset speed multiplier or Wi-Fi throughput benchmark. The physical Canon/phone network must still be retested. The deleted original-header operation’s old checks were removed; original transfer origin confinement and metadata parsing remain covered.
